## 1. Component Overview

My component develops the data layer connecting the project's sensing,
AI, and monitoring components. It is designed to receive fabric-related
sensor data, validate and standardize it, store it reliably, associate
outputs with the correct fabric sample, and make the information
available to other parts of the system.

The goal is to provide one consistent, traceable data layer across the
fabric-analysis workflow, rather than treating sensor readings, AI
predictions, and defect-detection results as disconnected outputs.

## 2. My Role and Responsibilities

-   Receive sensor messages through MQTT.
-   Validate incoming payloads and reject malformed or incomplete data.
-   Standardize fields, timestamps, and sample identifiers.
-   Store readings in a database and retrieve historical records.
-   Connect Node-RED data flows to cloud database storage.
-   Develop API endpoints for readings and analysis results.
-   Integrate fabric-classification and defect-detection outputs with the correct sample records.
-   Add error handling, logging, and data-quality checks.
-   Test the data pipeline and evaluate its reliability and performance.

## 5. Research Novelty and Contribution

### Proposed novelty: a traceable, sensor-to-decision data integration layer

The potential novelty of my component is not simply storing sensor
readings in a database. It is designing a **sample-centred, traceable
data integration layer** that connects multiple types of evidence about
the same fabric sample across the system.

The proposed contribution includes:

1.  **Sample-level data traceability:** use a consistent sample
    identifier and timestamps to associate sensor readings, AI
    classification outputs, and defect-detection results with the same
    fabric sample.
2.  **Data quality at ingestion:** validate and standardize messages
    before storage, reducing the risk of malformed or inconsistent
    records affecting downstream analysis.
3.  **Unified sensor and AI results:** provide a structured way to
    combine physical sensor measurements with machine-learning
    predictions and computer-vision defect results, rather than leaving
    them in disconnected components.
4.  **Local-to-cloud data architecture:** develop and test the pipeline
    locally while establishing a Node-RED-to-Neon DB connection for
    cloud storage and access.
5.  **A foundation for research analytics:** preserve structured
    historical data for investigating sensor reliability, classification
    confidence, unusual readings, processing delays, and relationships
    between sensor measurements and fabric-analysis outcomes.

These are proposed research contributions. Their novelty should be
evaluated against related work and demonstrated through implementation
and experiments. Do not present them as proven first-of-their-kind
claims without a literature review.

## 6. Research Scope and Future Extensions

The component has scope beyond basic database storage. Potential
extensions include:

-   **Sensor-data anomaly detection:** flag implausible readings, sudden
    changes, or possible sensor faults.
-   **Data quality scoring:** measure completeness, validity,
    consistency, and freshness of incoming records.
-   **End-to-end traceability:** maintain a history of each sample from
    conveyor detection through sensing, classification, defect analysis,
    and final output.
-   **Real-time performance evaluation:** measure message-processing
    latency, database write latency, API response time, throughput, and
    data loss.
-   **Reliability testing:** test malformed payloads, missing fields,
    duplicate messages, interrupted broker connections, and database
    outages.
-   **Local and cloud comparison:** compare local database operation
    with cloud persistence for latency, availability, and deployment
    suitability.
-   **Historical analytics:** visualize patterns across samples,
    readings, classifications, and detected defects.
-   **Model monitoring support:** store model version, prediction
    confidence, and result timestamps if supplied by the AI component.
-   **Data lineage and auditability:** record where each result
    originated, when it was produced, and which sample it describes.
-   **Integration API:** provide documented endpoints for live readings,
    sample history, classifications, and defect results.

Machine learning for anomaly detection is a possible extension, not a
completed feature unless a model has been implemented and evaluated.
